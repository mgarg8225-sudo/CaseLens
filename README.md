# CaseLens

Privacy-first analytics that link fragmented case records from police, hospitals, forensic labs, prosecutors and courts, without a common ID, to show where violence-against-women cases stall or drop out of the system.

**Synthetic data only.** No real survivor data was used. This is a prototype for demonstration, not a production system.

## The problem

When a violence-against-women case moves through the system, each agency keeps its own records with no shared identifier. Names are spelled differently, dates are off, fields are missing. Because of this, nobody can see the full journey of a case, or where cases get delayed or dropped.

## What CaseLens does

| Requirement | How it is addressed | Where |
|---|---|---|
| Link records without a common ID | Probabilistic record linkage (Fellegi-Sunter model, Splink) with name normalization, phonetic encoding and multiple blocking rules | `src/linkage.py` |
| Reconstruct case journeys | Linked records become an event log: FIR, medical exam, forensic report, chargesheet, trial, verdict | `src/journey.py` |
| Find delays and drop-offs | Stage, district and case-category analytics, with leak-point detection | `src/analytics.py` |
| Trends without targeting individuals | Dashboard shows aggregates only | `app/dashboard.py` |
| Measure and manage linkage errors | Precision, recall and F1 against ground truth; uncertain pairs go to a human review queue | `src/evaluate.py`, `data/review_queue.csv` |
| Protect survivor identity | Differential privacy (Laplace mechanism) with a privacy budget; no names or IDs in aggregate outputs | `src/privacy.py` |

## Data

All data is generated by `src/generate_data.py` with a fixed random seed. It creates about 5,000 true cases across 8 fictional districts and 5 case categories, split into five agency tables with different schemas. Realistic noise is injected: spelling and transliteration variants, swapped names, missing fields, date errors and duplicates. Drop-off rates and delays differ by district, and a few leak points are injected on purpose so the analytics have something to find.

The ground-truth case ID exists only in `data/ground_truth.csv` and is used only for evaluation.

## Findings the system detects

The system recovers the leak points injected into the data, for example slow forensic turnaround in one district and a high FIR-to-chargesheet drop-off in another. Because these were injected, this shows the pipeline can find such problems, not that they exist in real data.

## Privacy approach

- Dashboard outputs are aggregates only.
- Counts are protected with epsilon-differential privacy (Laplace noise), with sequential-composition budget accounting.
- Differential privacy bounds re-identification risk; it does not make it zero.
- Raw names and addresses never reach the dashboard.

## Limitations

- Synthetic data; real-data accuracy is not tested.
- Dashboard login and role-based access are not implemented yet. Authentication code exists (`src/auth.py`) but is not wired into the dashboard.
- Differential privacy parameters are illustrative and need expert review before real use.
- Deployment would need data-sharing agreements, legal review (including India's DPDP Act 2023) and a security audit.

## Future work

- Role-based access control and audit logging for agency users
- Human-in-the-loop review of uncertain matches, feeding decisions back into clustering
- Pilot on a small anonymised sample from one district
